# [草稿] Flow vs Channel & SharedFlow vs StateFlow

> 建立日期：2025-07-14
> 文章編號：657
> 狀態：草稿 (Draft)

---

在 Kotlin Coroutines 的世界裡，`Flow` 和 `Channel` 都是處理非同步資料流的利器，但它們就像是廚房裡的兩種截然不同的工具：**食譜**與**輸送帶**。

#### 一切從「冷」與「熱」說起

* **`Flow` 是一份「食譜」(Recipe) — 它是冷的、聲明式的。** 一份食譜本身只是藍圖，詳細描述了從備料到上菜的每一個步驟。它本身不會產生任何菜餚，直到有廚師（消費者）決定照著它開始烹飪 (`collect`)，整個流程才會從頭開始。每個廚師拿到的都是全新的、專屬於自己的烹飪流程。

* **`Channel` 是一條「輸送帶」(Conveyor Belt) — 它是熱的、實體的。** 一條輸送帶是工廠裡真實存在的溝通橋樑。它獨立運轉，生產線一端的機器（生產者）可以隨時把零件放上去，而不管另一端的工人（消費者）是否正在等待。這條輸送帶是所有工人共享的，一個零件被拿走，另一個工人就拿不到了。

#### 我到底該用哪個？

**絕大多數情況下，請優先使用 `Flow`**

當你的需求符合以下任一點時，`Flow` 都是更安全、更簡潔的選擇：

1. **單向資料流場景**：這是 `Flow` 的主場。從資料庫或網路 API 獲取資料，經過一系列轉換 (`map`, `filter`)，最後顯示在 UI 上。這就是典型的 `Repository -> ViewModel -> UI` 模式。

2. **資料需要時才載入（Lazy Loading）**：你希望只有當 UI 真的開始觀察資料時，才觸發網路請求或資料庫查詢。`Flow` 的冷流特性完美符合這個需求。

3. **需要自動的生命週期管理**：你希望當使用者離開畫面時，所有相關的資料流動都能自動停止，避免記憶體洩漏。`Flow` 與 `協程Scope` 的結合讓這一切變得輕而易舉。

> 

**一句話總結：當你想「描述」一個非同步資料序列時，用 `Flow`。**

** 在特定、低階的場景下，才考慮使用 `Channel`**

`Channel` 更像一個低階的併發工具，而不是一個資料流 API。當你的需求符合以下情況時，它才能發揮所長：

1. **Coroutine間的同步通訊**：你有兩個或多個**獨立且並行**的Coroutine，需要一個安全的管道來互相傳遞事件或資料。`Channel` 在此扮演了「同步佇列」的角色。

2. **工作佇列模式 (Work Queue)**：一個 Boss Coroutine不斷地透過 `Channel` 分派任務，而一群「工人」Coroutine則從同一個 `Channel` 競爭獲取任務來處理。這能有效地將工作分發給多個併發單元。

3. **事件的標準化處理**：你需要確保一個事件**只被一個消費者處理**。例如，多個 UI 事件源彙整到一個 `Channel`，由單一的Coroutine來消費，避免重複處理。

> 

**當你需要處理多個Coroutine**s**之間的「通訊與同步」問題時，才考慮 `Channel`。**

#### `SharedFlow` 與 `StateFlow`

衍生推出了 `StateFlow` 和 `SharedFlow`。

* **`StateFlow`**：一個專門用來持有「狀態」的熱流。它是 `LiveData` 在Coroutine世界的完美繼任者。

* **`SharedFlow`**：一個通用的、可配置的熱流，用於向多個訂閱者「廣播」事件。

許多過去可能需要用 `Channel` 來實現的事件廣播或狀態共享需求，現在都可以被這兩位 `Flow` 的「熱心」親戚以更安全、更聲明式的方式取代。這也讓 `Channel` 的定位更加清晰：它是一個強大的低階併發原語，而不是日常應用的首選。
