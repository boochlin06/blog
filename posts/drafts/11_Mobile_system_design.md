## 一個簡單的行動系統設計面試框架 (iOS & Android)

本指南提供了一個應對行動系統設計面試的框架，特別是針對 iOS 和 Android 的職位。核心理念是，面試官的重點在於評估你的**思維過程**和**溝通技巧**，而不是期望你在有限的時間內提出一個完美的、可直接上線的解決方案。透過展示你的強項，你可以提升作為候選人的整體評價。

歡迎加入 ["Mobile System Design"](https://www.google.com/search?q=https://discord.gg/b5N22aJq) Discord 伺服器進行一般性討論和回饋。

### 免責聲明

這個框架的靈感來自於「可擴展後端設計 (Scalable Backend Design)」的相關資源。理解本指南**不保證**成功。面試結構會因面試官的風格而異。**積極的對話至關重要**——多問釐清性的問題，避免做出假設。

本指南**不**反映 Google (或任何其他公司) 的面試政策。

---

### 面試流程 (45–60 分鐘)

* **2–5 分鐘：** 自我介紹

* **5 分鐘：** 任務定義與需求收集

* **10 分鐘：** 高層次討論

* **20-30 分鐘：** 細節討論

* **5 分鐘：** 向面試官提問

---

### 自我介紹

簡要分享你的相關經驗。範例：「你好，我是 Alex。我從 2010 年開始開發 iOS/Android，專注於框架和函式庫。在過去的 2.5 年裡，我帶領一個團隊負責 XYZ 專案，涵蓋了系統設計、規劃和技術指導。」目的是為了打破僵局並突顯相關技能。

---

### 定義任務

面試官會提出任務，例如「設計 Twitter 的動態摘要 (Feed)」。首先要確定任務的範疇：

* **僅限客戶端：** 在給定後端和 API 的情況下設計 App。

* **客戶端 + API：** 設計客戶端 App 和 API。(**最常見**)

* **客戶端 + API + 後端：** 設計 App、API 和後端。(較不可能)。如果你的後端經驗有限，請坦誠相告。專注於你的行動開發專業知識，並提及你從書籍、影片等對後端概念的高層次理解。

---

### 收集需求

將需求分為**功能性**、**非功能性**和**超出範疇**。以「設計 Twitter 動態摘要」為例：

#### 功能性需求

專注於高價值的特性 (3-5 個)。

* 使用者可以滾動瀏覽無限的推文摘要。

* 使用者可以「喜歡」一則推文。

* 使用者可以查看特定推文的留言 (唯讀)。

#### 非功能性需求

這些對於產品的整體成功至關重要。

* **離線支援**：即使沒有網路連線，使用者也應該能查看快取的推文並與之互動。

* **即時通知**：通知使用者有新的推文、喜歡和留言。

* **最佳化資源使用**：最小化頻寬、CPU 和電池消耗。考慮網路優化技術和高效的資料處理。

#### 超出範疇

排除那些對真實專案很重要，但在面試範疇之外的功能。

* 登入/認證

* 發送推文

* 追蹤/轉推

* 分析

---

### 提供「信號 (Signal)」

面試官評估的是你的思考過程。向他們展示：

* 你的**假設**以及你如何清楚地陳述它們。

* 你選擇特定功能背後的**理由**。

* 相關的**釐清性問題**。

* 對**權衡取捨**和潛在問題的意識。

**多問問題**並涵蓋不同方面。採用**廣度優先搜尋 (BFS)** 的方法，然後詢問面試官他們想深入探討哪個領域。如果他們讓你選擇，就選一個你熟悉的議題。

---

### 釐清性問題

在任務釐清階段提出這些問題：

* **我們需要支援新興市場嗎？**

  * 考慮到低階設備和昂貴的數據費用，需要優化 App 大小。優先考慮快取並最小化網路請求。在 Android 上，研究使用 App Bundles；在 iOS 上，研究 App Thinning。

* **我們預期有多少使用者？**

  * 大量使用者會影響後端負載。討論**指數退避 (Exponential Backoff)** 和 **API 速率限制 (Rate Limiting)** 以防止意外的 DDoS 攻擊。

* **工程團隊有多大？**

  * 小團隊 (2-4人) 與大團隊 (20-100人) 的考量不同。專注於**模組化**和專案結構，以實現並行開發。思考使用 Monorepo 與 Multi-repo 策略。

* **目標作業系統版本和設備類型是什麼？**

  * 這將影響架構模式的決策 (例如 Compose/SwiftUI vs. 舊的 View 系統)、可用的 API (例如背景任務、資料持久化) 和必要的相容性層。

* **是否有我們需要達成的特定效能基準？**

  * 了解摘要更新、圖片載入和其他關鍵互動的可接受延遲。這將影響快取策略、網路優化和資料序列化技術。

* **需要什麼級別的資料一致性？**

  * 對於「喜歡」和「留言」，我們能否容忍**最終一致性 (eventual consistency)**，還是需要**強一致性 (strong consistency)**？這會影響離線行為和資料同步策略的決策。

* **資料更新的頻率如何？**

  * 如果推文非常頻繁，基於**拉取 (pull-based)** 的刷新策略可能會使伺服器不堪重負。推播通知或 SSE (Server-Sent Events) 可能更合適。

* **預期的媒體類型是什麼？**

  * 圖片的大小和格式將影響快取和網路策略。考慮支援現代格式，如 **webp** 或 **AVIF**。影片則需要不同的考量，例如串流協定 (HLS, DASH)、轉碼和 CDN 支援。

### 高層次圖表

如果面試官滿意，詢問他們是否想看一個高層次圖表。

**伺服器端元件：**

* **後端 (Backend)**：整個伺服器基礎設施。專注於客戶端的考量。

* **推播供應商 (Push Provider)**：用於行動推播通知的基礎設施。從後端傳遞 payload。

* **CDN (內容分發網路)**：高效地向客戶端分發靜態內容（圖片、影片）。

**客戶端元件：**

* **API 服務 (API Service)**：抽象化客戶端-伺服器通訊。提供與後端互動的乾淨介面。考慮使用像 Retrofit (Android) 或 Alamofire (iOS) 的函式庫。

* **持久化層 (Persistence)**：設備上資料的**單一事實來源 (single source of truth)**。資料先在本地持久化，然後傳播到其他元件。這使得離線存取成為可能並減少了網路依賴。

* **儲存庫 (Repository)**：API 服務和持久化層之間的中介。將資料來源與 UI 解耦。

* **推文摘要流程 (Tweet Feed Flow)**：負責顯示可滾動推文列表的元件。

* **推文詳情流程 (Tweet Details Flow)**：負責顯示單一推文詳情的元件。

* **DI 圖 (DI Graph)**：依賴注入圖。實現鬆耦合和可測試性 (Android 上的 Dagger/Hilt，iOS 上的 Swinject/Typhoon)。

* **圖片載入器 (Image Loader)**：載入並快取圖片 (Android 上的 Glide/Coil，iOS 上的 SDWebImage/Kingfisher)。

* **協調器 (Coordinator)**：管理推文摘要和推文詳情之間的導航和流程邏輯，將元件解耦。

* **App 模組 (App Module)**：系統的可執行部分，將各元件「黏合」在一起。負責應用程式生命週期管理。

* **分析服務 (Analytics Service)**：負責收集和傳輸分析資料的模組，例如使用者行為和效能指標。

#### 提供「信號」

面試官尋找的是：

* 在不陷入不必要細節的情況下，呈現「大局」的能力。

* 識別主要建構模組及其互動。

* 對 App 模組化和團隊協作的考量。

#### 常見問題

* **為什麼高層次圖表是必要的？我可以跳過嗎？**

  * 不是強制性的，但它有優勢：

    * **時間管理**：快速概述系統並提出討論點。

    * **模組化**：每個元件都可以是一個獨立的模組，便於團隊協作。

    * **最佳實踐**：與後端系統設計和用於視覺化架構的 [C4 模型](https://c4model.com/)相呼應。

  * **仍然不確定？** 詢問面試官他們是想要圖表還是希望直接進入特定元件。

### 深入探討：推文摘要流程

面試官可能會專注於某個特定元件，例如「推文摘要流程」。討論：

* **架構模式**：MVP, MVVM, MVI, Clean Architecture, Redux。通常不鼓勵使用 MVC。選擇一個知名的模式以便於新人上手。

* **分頁 (Pagination)**：無限滾動的基礎。(見分頁部分)。

* **依賴注入 (Dependency Injection)**：改善模組隔離和可測試性。

* **圖片載入**：討論低解析度佔位圖、全解析度載入和滾動效能。

**元件**

* **摘要 API 服務 (Feed API Service)**：抽象化 Twitter 摘要 API 客戶端，獲取分頁資料。透過 DI 注入。

* **摘要持久化層 (Feed Persistence)**：抽象化快取的分頁資料儲存。透過 DI 注入。

* **遠端中介器 (Remote Mediator)**：獲取下一頁/上一頁的資料並將其儲存到持久化層。

* **摘要儲存庫 (Feed Repository)**：使用遠端中介器將遠端和快取的回應合併成一個 `Pager` 物件。

* **分頁器 (Pager)**：觸發從遠端中介器獲取資料，並向 UI 公開一個可觀察的分頁資料流。

* **"喜歡推文" 和 "推文詳情" Use Cases**：實現「喜歡」和「顯示詳情」的操作。透過 DI 注入。

* **圖片載入器 (Image Loader)**：抽象化圖片載入函式庫的圖片載入功能。透過 DI 注入。

#### 提供「信號」

面試官評估的是：

* 對常見 MVx 模式的熟悉度。

* 業務邏輯和 UI 的分離。

* 對依賴注入的理解。

* 設計自包含模組的能力。

#### 常見問題

* **我應該提供多少細節？**

  * 沒有嚴格的規則。與面試官合作；詢問他們是否需要更多細節或想繼續下個主題。觀察他們的肢體語言。如果他們打斷你，停下來問他們是否有問題。**合作是關鍵**。

* **為什麼沒有提到特定的類 (RecyclerView/UICollectionView) 或供應商 (Room, CoreData, Realm)？**

  * 為了保持指南的平台無關性。函式庫發展迅速。抽象化功能更為穩健。

  * 供應商的選擇是主觀的，基於經驗/趨勢。

  * 大公司通常會建立自訂的技術棧。

  * 實作細節在網路上隨處可見。

* **我應該使用什麼繪圖工具？**

  * **Excalidraw**, **Google Jamboard**, 和 **Google Drawings** 很受歡迎。有些人偏好協作編輯器和口頭討論。隱私政策可能會限制工具的選擇。

### API 設計

盡可能多地涵蓋各個方面。詢問面試官是否有偏好，或者選擇一個你熟悉的領域。

#### 即時通知

討論即時更新的方法：

* **推播通知 (Push Notifications)**

  * **優點**：易於實現、可以喚醒背景中的 App、(正確使用時) 省電。

  * **缺點**：不是 100% 可靠、可能有延遲、依賴第三方服務、使用者可以選擇退出、可能被濫用 (垃圾訊息)。

* **HTTP 輪詢 (HTTP-polling)**

  * 定期請求更新。可能產生過多流量和後端負載。

  * **短輪詢 (Short polling)**：固定時間間隔。

    * **優點**：實現簡單、無持久連接、相容防火牆、易於水平擴展、(如果不頻繁) 成本較低、可用於批次更新。

    * **缺點**：可能有顯著延遲、TLS 握手和 HTTP 標頭的開銷、頻寬使用效率低、伺服器負載高。

  * **長輪詢 (Long polling)**

    * **優點**：近乎即時的通知。

    * **缺點**：更複雜，需要更多伺服器資源、保持一種「偽」持久連接、仍有延遲、易受連接超時和中斷影響、擴展更複雜。

* **伺服器發送事件 (Server-Sent Events - SSE)**

  * 透過 HTTP 串流事件，無需輪詢。

  * **優點**：單一連接的即時更新、比 WebSockets 簡單、標準協定、比長輪詢開銷低、基於文本的協定。

  * **缺點**：保持持久連接、單向通訊 (伺服器到客戶端)、舊瀏覽器支援有限、有連接限制。

* **WebSockets**

  * 雙向通訊。

  * **優點**：可傳輸二進位和文本資料、全雙工通訊、比 HTTP 輪詢延遲低、頻寬使用效率高。

  * **缺點**：設置更複雜、保持持久連接、擴展更複雜、防火牆問題、安全問題增加、電池消耗較高、比 HTTP 更難偵錯。

為「設計 Twitter 摘要」選擇一個合適的方法。**SSE** (作為「喜歡」更新和可能的新推文通知的主要通道) 和 **推播通知** (用於沒有活動連接的客戶端或不太重要的更新) 的組合可能很合適。

### 協定 (Protocols)

* **REST (表象化狀態傳輸)**

  * **優點**：易於學習和實現、易於使用 HTTP 快取、鬆耦合、無狀態、廣泛支援、人類可讀。

  * **缺點**：在行動裝置上效率較低、無 schema、無狀態需要額外功能來維護會話、元數據和標頭的開銷、過度獲取/獲取不足 (Over-fetching/Under-fetching)。

* **GraphQL**

  * **優點**：基於 schema 的類型化查詢、高度客製化、透過 Subscriptions 支援雙向通訊、強類型、版本控制不那麼關鍵、優秀的開發者工具。

  * **缺點**：後端更複雜、「 leaky abstraction (抽象洩漏)」、查詢效能取決於最慢的服務、快取複雜、安全考量。

* **WebSocket**

  * **優點**：即時雙向通訊、支援文本和二進位資料、低延遲、高效的頻寬使用。

  * **缺點**：需要維護活動連接、無 schema、每個伺服器的活動連接數有限、比 HTTP 輪詢或 SSE 更複雜、有狀態。

* **gRPC (gRPC 遠端程序呼叫)**

  * **優點**：輕量級二進位訊息、基於 schema、支援事件驅動架構、多個並行請求、高效能、強類型、在不可靠網路上表現良好。

  * **缺點**：瀏覽器支援有限、非人類可讀格式、學習曲線陡峭、比 REST 複雜、客戶端較重、不如 REST 廣為人知。

* **MQTT (訊息佇列遙測傳輸)**

  * **優點**：輕量級、發布-訂閱模式、即時通訊、服務品質 (QoS) 等級。

  * **缺點**：二進位協定、不如基於 HTTP 的協定廣泛使用、有狀態、安全考量、依賴中介 (Broker)。

選擇一個合適的協定。對於「設計 Twitter 摘要」，**REST** 很合適，因為它對於許多初始任務來說很簡單。對於未來更複雜的資料獲取需求，可以考慮 **GraphQL**。

### 分頁 (Pagination)

對於返回列表的端點至關重要，可防止過度的網路和記憶體使用。

* **偏移分頁 (Offset Pagination)**

  * `limit` 和 `offset` 參數。

  * **優點**：易於實現、伺服器端無狀態、易於理解。

  * **缺點**：大偏移量時效能差、新增/刪除行時不一致 (頁面漂移)、不適合即時摘要、易受參數操縱。

* **鍵集分頁 (Keyset Pagination)**

  * 使用上一頁最後一項的值來獲取下一組項目。

  * **優點**：易於轉換為 SQL、大數據集效能好、伺服器端無狀態、對插入操作更有彈性。

  * **缺點**：「抽象洩漏」、僅適用於具有自然排序的欄位、可能存在平局問題、對資料修改敏感、隨機存取不靈活。

* **游標/搜尋分頁 (Cursor/Seek Pagination)**

  * 使用封裝分頁狀態的不透明游標或 token。

  * **優點**：將分頁與 SQL 解耦、插入/刪除新項目時排序一致、更靈活、隱藏實現細節。

  * **缺點**：後端更複雜、游標過期或失效時會出問題、仍可能對項目刪除敏感、透明度較低、不易加入書籤。

* **頁碼分頁 (Page Number Pagination)**

  * 使用頁碼和頁面大小參數。

  * **優點**：使用者易於理解、(初期) 實現簡單。

  * **缺點**：繼承了偏移分頁的所有缺點、不適合無限滾動、不適合即時資料。

選擇一種方法。對於「設計 Twitter 摘要」，**游標分頁**是合適的，因為它將分頁與底層資料儲存解耦，並且能很好地處理插入/刪除。

### 資料儲存

* **本地設備儲存選項**

  * **鍵值儲存 (Key-Value Storage)**：用於簡單、非結構化、非關聯性的資料。

  * **資料庫/ORM**：用於大型、結構化、需要複雜查詢的關聯性資料。

  * **自訂/二進位 (Custom/Binary)**：用於需要最大化控制效能和資料格式的自訂序列化。

  * **設備上安全儲存**：用於敏感資料、加密金鑰等。

  * **檔案儲存**：用於圖片、影片等大型非結構化資料。

* **儲存位置**

  * **內部 (Internal)**：沙盒化，App 私有。

  * **外部 (External)**：公開可見，可被其他 App 存取。

  * **媒體/範圍儲存 (Media/Scoped)**：外部儲存的受限子集，專門用於媒體檔案。

* **儲存類型**

  * **文件 (Documents)**：使用者生成的、不易重新產生的資料 (會自動備份)。

  * **快取 (Cache)**：可重新產生的資料 (系統可能會刪除)。

  * **暫存 (Temp)**：臨時資料 (系統隨時可能刪除)。

#### 應對方法

對於「設計 Twitter 摘要」：

* **摘要分頁表 (Feed Pagination Table)**

  * 使用 Room (Android) 或 Core Data (iOS) 儲存分頁的摘要資料。

  * 限制總條目數 (例如 500) 以控制本地儲存大小。

  * 將附件 (attachments) 扁平化為逗號分隔的 URL 列表或 JSON。

* **附件儲存 (Attachments Storage)**

  * 將附件（圖片、影片）作為檔案儲存在內部快取儲存中。

  * 使用附件 URL 作為快取鍵。

  * 限制快取大小 (例如 200-400 MB)。

### 其他主題

#### 行動開發的主要考量

* **使用者資料隱私**：資料洩露會損害商譽。

* **安全性**：防止逆向工程、資料外洩。

* **目標平台的變化**：新的作業系統版本可能會限制功能。

* **已發布產品的不可逆性**：使用階段性推出和伺服器端功能標記。

* **效能/穩定性**：計量數據使用、頻寬、CPU、記憶體、啟動時間、崩潰/ANR、電池消耗。

* **地理位置使用**：不要損害隱私，使用最低必要精度。

* **第三方 SDK 使用**：SDK 可能導致效能下降、安全漏洞。

#### 隱私與安全

* 最小化使用者資料收集。

* 最小化權限使用。

* 安全的資料儲存（加密所有靜態敏感資料）。

* 安全的通訊 (HTTPS)。

* 程式碼安全（混淆）。

* 隱私設計 (Privacy by Design)。

* 定期安全更新。

* 隱私合規 (GDPR, CCPA)。

* 透明度和使用者教育。

#### 雲端 vs. 設備端

* **雲端優點**：與設備無關、更好地利用客戶端資源、快速的變更節奏、更大的計算資源、更好的安全性、更容易的分析。

* **雲端缺點**：延遲增加、網路依賴、成本、安全風險、合規挑戰。

* **設備端優點**：更好的隱私、即時功能、更低的頻寬使用、離線功能、更低的後端使用。

* **設備端缺點**：設備限制、效能不一致、更大的 App 大小、難以更新、安全風險、電池消耗。

* **永遠不要在設備上運行的事**：敏感資源的創建（優惠券）、交易和支付驗證、複雜的業務邏輯或敏感演算法。

#### 離線與樂觀狀態 (Offline and Opportunistic State)

* 離線狀態確保 App 在沒有網路時的可用性。

* UI「樂觀地」更新，假設請求將在連上網路後發送。

* 狀態變更被批次處理，並在網路恢復時發送。

#### 請求去重複 (Request de-duplication)

* 確保重試請求不會在伺服器上創建重複項（**冪等性 - idempotence**）。

* 使用客戶端生成的唯一請求 ID 和伺服器端去重複機制。

* 使用 `Idempotency-Key` HTTP 標頭。

#### 同步本地與遠端狀態

* **本地衝突解決** (通常**不**推薦)：本地設備合併遠端與本地狀態並上傳。不安全，可能導致資料遺失。

* **遠端衝突解決** (推薦)：本地設備發送其本地狀態到後端，接收一個**完整**的新狀態，並覆蓋本地狀態。將衝突解決權交給後端。

#### 服務品質 (QoS)

* **限制並行網路操作**：4-10 個並行操作為佳。

* **網路請求優先級**：將請求分為不同 QoS 等級。

  * **使用者關鍵 (高)**：直接影響使用者體驗的請求。

  * **UI 關鍵 (中)**：影響 UI 反應性的請求。

  * **UI 非關鍵 (低)**：增強 UI 但非必要的請求。

  * **背景 (最低)**：在背景執行且不直接影響使用者的請求。

* 使用**優先級佇列**進行調度。

#### 可恢復上傳 (Resumable Uploads)

* 將大檔案分解成小塊上傳，允許暫停和恢復。

* **優點**：可恢復中斷的傳輸、提高可靠性、優化頻寬、進度監控。

* **缺點**：額外的連接和元數據開銷、增加複雜性、需要伺服器端支援。

#### 預取 (Prefetching)

* 主動獲取未來可能需要的資料或資源，以提高效能。

* **優點**：改善效能、增強使用者體驗、增加使用者參與度。

* **缺點**：增加頻寬、電池和儲存消耗、可能獲取到過期資料、資源浪費。

* **實施考量**：網路狀況、設備狀態、使用者行為、資料過期問題、快取管理。

### 結論

* **你能控制的事**：你的心態、你的準備、你的知識庫、你闡述思維過程的方式、你的履歷。

* **你無法控制的事**：面試官的風格和偏見、競爭、招聘委員會的決定。

**擁抱過程，從每次經驗中學習。** 失敗是過程的一部分。持續練習，持續學習。

### 常見問題與解答

* **Q: 這個方法如何知道是有效的？**

  * A: 它提供了一個結構化的框架，幫助雙方專注於討論的**內容**，而不是面試的組織方面。

* **Q: 你能更深入地講講 [某個技術/模式] 嗎？**

  * A: 本指南旨在提供一個廣泛的概述。你需要利用個人經驗來提供具體解決方案。

* **Q: 我是面試官——這份指南會不會鼓勵候選人背誦答案？**

  * A: 系統設計比程式挑戰更微妙。僅靠背誦通常不夠。這份指南旨在提供基礎理解，成功取決於候選人的批判性思維和應用知識的能力。

* **Q: 如果面試官想專注於我不熟悉的技術怎麼辦？**

  * A: 誠實面對。承認你的知識有限，解釋你對相關概念的一般理解，並強調你願意學習。

* **Q: 繪製圖表有多重要？**

  * A: 圖表非常有幫助。如果你不擅長，請事先練習。

* **Q: 我該如何處理與面試官的分歧？**

  * A: 尊重地、專業地處理。清楚闡述你的理由，並願意考慮其他觀點。

* **Q: 如果我卡住了怎麼辦？**

  * A: 不要恐慌。大聲說出你的思考過程，並向面試官尋求提示或指導。

* **Q: 我應該在不同架構模式 (MVP, MVVM, MVI 等) 之間如何選擇？**

  * A: 沒有單一的「最佳」模式。準備好解釋不同模式的優缺點，並根據專案需求證明你的選擇。

### 不同工程師級別的期望

* **初級工程師 (Junior Engineer)**

  * 系統設計面試通常是可選的。重點是基礎知識和實現定義明確的小元件。

* **中級工程師 (Mid-Level Engineer)**

  * 強調實際實現和架構模式的應用。能夠將高層次需求轉化為具體的實現細節。

* **高級工程師 (Senior Engineer)**

  * 轉向更高層次的視角。重點是系統架構、元件互動和可擴展性。

* **資深工程師 (Staff Engineer)**

  * 從技術考量轉向戰略考量。優先考慮業務需求，解釋如何縮短上市時間、安全地推出功能和處理大規模故障。
