## 一、 風格注入核心規範（對標 Blog 00 手寫招牌風格）

1. **角色定位**：資深 Android 系統與底層架構師，被丟去扛百元級弱雞晶片（高通 QM215），認命但不躺平、幽默自嘲但刀刀見血。
2. **破局五部曲公式**：
   * **第一步：亮底牌數落硬體**（4 顆 1.3GHz A53、2GB RAM、無 NPU、開機吃 1.3GB）。
   * **第二步：對比殘酷需求**（金融級 BCTC 認證、< 1 秒開門、99.99% 精度、7x24 不死機）。
   * **第三步：小學算術打臉**（以單行加減法等式直呼物理死局，接「RAM 直接炸裂」）。
   * **第四步：直球下刀底層代碼**（AOSP Makefile 裁減、內核調優、C++ NEON、FastCV、ACL SGEMM）。
   * **第五步：老鳥防坑口訣收尾**（例如「飛機起飛前先裝儀表板」、「把系統壓到剩骨頭，AI 才能長肌肉」）。
3. **格式排版**：零 Emoji、無 Markdown 表格、口語自然流暢的台灣繁體中文。
4. **絕對機密防線**：全面去識別化，0 雲端後台敏感詞、0 廠商品牌前綴、0 內部專案代號、0 私有套件路徑。

## 二、 全系列 17 篇文章改寫重點與核心算式對照

### 階段 1：硬體瓶頸量測與系統減磅

#### 00 篇：到底有多爛？（風格基準篇）
* **檔案名稱**：`00_Android_爛裝置想跑人臉辨識0_–_到底有多爛？.md`（文章 ID 401）
* **風格核心**：全系列風格母本，揭露 QM215 物理硬傷與 BCTC 認證死局。
* **經典算式**：`2048MB (實體) - 1300MB (系統) - 950MB (雙相機) = -202MB < 0`

#### 01 篇：評估第一
* **檔案名稱**：`01_Android_爛裝置想跑人臉辨識1_–_評估第一.md`（文章 ID 461）
* **改寫亮點**：引入「沒有儀表板的飛機沒人敢開」現場感；拆解 dumpsys meminfo、procrank、smaps，定義 USS、PSS、RSS。
* **核心算式**：全機 Free RAM 表面 456MB，揭露扣除 cached 後真正自由空間只有可憐的 64MB。

#### 02 篇：記憶體優化：無用系統服務徹底剔除
* **檔案名稱**：`02_Android_爛裝置想跑人臉辨識2_–_記憶體優化_無用系統服務out.md`（文章 ID 416）
* **改寫亮點**：分為第一階段 AOSP 標準規範（`go_defaults.mk`、`TARGET_NO_TELEPHONY`、permissions 拔除）與第二階段 Kiosk 極限抽脂（Launcher3、SystemUI、LatinIME、無電池、跳過 WebView 預載）。
* **核心算式**：`1300MB - 300MB (Go標準) - 220MB (Kiosk抽脂) = 780MB`，淨奪回 520MB 實體 RAM！

#### 03 篇：系統優化：ZRAM, SWAP, KSM 擴張最大值
* **檔案名稱**：`03_Android_爛裝置想跑人臉辨識3-_系統優化-ZRAM,SWAP,KSM，擴張最大值.md`（文章 ID 418）
* **改寫亮點**：剖析 DMA/ION Pinned 頁面不可壓縮物理本質；揭露 KSM 耗 10% CPU 僅省 20MB 果斷拔除；揭露 eMMC Swap 磨穿 Flash 顆粒定時炸彈；確立 256MB ZRAM LZ4 + `page-cluster=0` 克制藝術。
* **核心算式**：256MB ZRAM 壓縮比 2.8:1，收容 700MB 冷頁面，擠出 450MB 純淨實體記憶體。

### 階段 2：底層記憶體防線、LMKD 與 GC 決戰

#### 04 篇：記憶體控場師 LMKD
* **檔案名稱**：`04_Android_爛裝置想跑人臉辨識4_–_記憶體控場師LMKD.md`（文章 ID 431）
* **改寫亮點**：從 OOM Killer、In-kernel LMK 演進到 Userspace LMKD；對比 Vmpressure 與 Linux 4.20 PSI；修改 `ProcessList.java` 快取上限 32->3；排除雙殺手衝突。
* **核心算式**：可用 Free RAM 從瀕危的 64MB 暴增至 470MB，系統 Used RAM 從 1.5GB 壓制到 804MB。

#### 05 篇：GC 是唯一會關心你 OOM 的好人
* **檔案名稱**：`05_Android_爛裝置想跑人臉辨識5_–_GC_是唯一會關心你OOM_的好人.md`（文章 ID 453）
* **改寫亮點**：**徹底剔除原檔尾端冗長未整理的 230 行舊版草稿**；深度剖析 ART GC Log（`for alloc` vs `background` vs `NativeAlloc`）；第一性原理將大記憶體操作全面下沉 C++ Native；調優 `dalvik.vm` 參數。
* **核心算式**：相機每秒灌入 13.8MB YUV，若在 Java 分配每秒產生 40MB 垃圾，3 秒打滿 Heap；下沉 Native 後 Java Heap 恆定 15MB。

#### 06 篇：三路高頻影像流：三倍蓋亞，趕快 GC
* **檔案名稱**：`06_Android_爛裝置想跑人臉辨識6_–_三路高頻影像流_三倍蓋亞_趕快gc.md`（文章 ID 912）
* **改寫亮點**：五道手術：0-new 鐵碗隊列、單一可重用 Bitmap 鐵碗、雙層背壓 Drop-Oldest、階梯式漏斗淘汰（四大惡霸短路）、QFastCV Native 直轉。
* **核心算式**：`RGB 13.8MB/s + ToF 55.3MB/s = 69.1MB/s` 原始灌入，0.3ms 歸還硬體 Buffer，待機 CPU 負載從 100% 降至 15%~20%。

#### 07 篇：物理世界需要 watchdog
* **檔案名稱**：`07_Android_爛裝置想跑人臉辨識7_–_物理世界需要_watchdog.md`（文章 ID 895）
* **改寫亮點**：獨立 MCU 被閹割後的軟體自救：顯式靜態廣播冷啟動拉活進程；Linux NUD (ARP) 0 CPU 監控網卡硬體死鎖；相機斷流兩段式 GPIO 500ms 電擊與全機冷重啟。

#### 補充篇：GC Thrashing 思路補充
* **檔案名稱**：`07_1_Android_爛裝置想跑人臉辨識_–_GC_Thrashing_思路補充.md`（文章 ID 933）
* **改寫亮點**：揭露每 20ms 觸發一次 GC 清理 1KB 的瀕死現場；揪出第三方庫（OpenCV Mat、HAL wrapper）殘留 `finalize()` 塞爆 `FinalizerDaemon` 獨木橋；全面邁向顯式生命週期與 Cleaner。

### 階段 3：影像演算法極限榨汁與異質運算

#### 08 篇：YUV_420_888 還能怎樣加速：QFastCV
* **檔案名稱**：`08_Android_爛裝置想跑人臉辨識8_–_YUV_420_888_還能怎樣加速_QFastCV.md`（文章 ID 952）
* **改寫亮點**：人類視覺生理缺陷（視桿 1.2 億 vs 視錐 600 萬）；Semi-Planar NV21 硬體 ISP 掃描歷史；Row Stride 64-byte 對齊垃圾；Java 24 萬次邊界檢查（15ms）對比 QFastCV ARM NEON `VLD2` 向量拆分（< 1ms）。

#### 09 篇：兄弟齊心，軟硬兼施：ARM Compute Library (ACL)
* **檔案名稱**：`09_Android_爛裝置想跑人臉辨識9_–_兄弟齊心_軟硬兼施_arm_compute_lib.md`（文章 ID 943）
* **改寫亮點**：5,000 人 1:N 特徵比對演化史：純 Java 雙重迴圈 150ms -> JNI 頻繁換向災難 320ms -> ARM ACL SGEMM 3ms！蓋一萬份公文的辦公室 SOP 比喻（Prefetch、NEON 4 連體印章、32KB L1 Tiling 分塊、Packing 排布）。
* **核心算式**：`512 x 5000 = 256 萬次浮點乘加`，耗時從 320ms 降至 3ms，提速 100 倍。

#### 番外篇：從 50ms 到 3ms：ARM NEON、FastCV 與記憶體極限榨汁指南
* **檔案名稱**：`09_1_Android_爛裝置想跑人臉辨識_番外篇_–_從_50ms_到_3ms：ARM_NEON、FastCV_與記憶體極限榨汁指南.md`（文章 ID 1006）
* **改寫亮點**：記憶體牆（A53 讀 L1 1~3 時脈 vs DRAM 150~200 時脈）；SoA vs AoS 排布；4 大動刀點取捨真話（ToF 100% NEON、FastCV 主路徑高效+備援純 Java 保底、ACL 官方庫不炫技重造、冷開機 50 筆批次不寫 mmap）；全鏈路 Post 1 儀表板端到端驗收（1.5 秒降至 280ms）。

#### 11 篇：ToF RAW12 轉 3D 點雲
* **檔案名稱**：`11_Android_爛裝置想跑人臉辨識11_–_ToF_RAW12_轉_3D_點雲.md`（文章 ID 997）
* **改寫亮點**：30.7 萬點 3D 賽博龐克點雲即時渲染；5 道工序（C++ 幾何解算、空間距離過濾、sample 動態降採樣砍 80% GPU 負擔、7-Float 28 bytes 交錯排布、DirectBuffer 0-GC）；Atan2 查表法、NEON 8 像素並行、牛頓逼近開方消滅開根號延遲；OpenGL ES `GL_POINTS` 著色器繪製。

#### 12 篇：說到底還是一台 IOT：WebSocket 篇
* **檔案名稱**：`12_Android_爛裝置想跑人臉辨識12_–_說到底還是一台IOT-WebSocket.md`（文章 ID 1010）
* **改寫亮點**：為什麼必須用 WebSocket（0.1s 秒開門、無公網 IP NAT 穿透）；為什麼大檔案（50MB 韌體）必須留給 RESTful（防 TCP 隊頭阻塞）；Protobuf over WebSocket 幹掉 JSON Base64（省 60% 頻寬與記憶體，免 Envoy 代理）；HandlerThread 單執行緒事件隊列；SQLite 離線雙指針與 ACK 閉環。

#### 13 篇：為了幾乎不會用到的功能需要大改特改的 WebRTC
* **檔案名稱**：`13_Android_爛裝置想跑人臉辨識13_–_為了幾乎不會用到的功能需要大改特改的webrtc.md`（文章 ID 1015）
* **改寫亮點**：Android `cameraserver` 排他性衝突；血淚遺產「sleep 5 秒」與 `onClosed` 假通知真相；掛斷通話 0ms 搶相機 `CAMERA_IN_USE` 死鎖黑屏；終極解法：**永遠不關相機**，以單一相機常駐源 + `ExternalVideoCapturer` + 帶釋放回調的 3 槽安全物件池，切換耗時從 5000ms 降至 0ms。

#### 14 篇：門禁機當 BLE Peripheral 的現場踩坑記
* **檔案名稱**：`14_Android_爛裝置想跑人臉辨識14_–_門禁機當_BLE_Peripheral_的現場踩坑記.md`
* **改寫亮點**：施工現場無觸控、強光反光情境；角色倒轉為 BLE Peripheral（0% CPU 開銷保護 30fps 人臉辨識）；31-Byte 雙層廣播拆分（短機號在第一層，128-bit UUID 在 ScanResponse）；死守 20-Byte 保底與 2-Byte 狀態機；拋棄 Notification 走 6-Byte 緊湊輪詢；7-Byte TLV 靜態 IP 配置與 DNS2 隱式 Commit。
